# Basic 2.0.0 source delivery

Basic finds MCP servers for a task and presents their setup requirements with dated catalog evidence. The source application uses PostgreSQL and serves a browser interface plus three read-only Streamable HTTP tools: `search_servers`, `get_server`, and `get_setup_instructions`.

## Download and install

Download `basic_2.0.0_source.zip` and its `.sha256` file from [v2.0.0](https://github.com/agammann/basic/releases/tag/v2.0.0). The ZIP contains the committed source, MIT license, dependency lockfile, 30 curated profiles, migrations and operator documentation. It does not include a database, dependencies or a built application. This guide retains its established file path; it describes v2, not the immutable v1.0.0 archive.

**Breaking upgrade boundary:** v2 initializes PostgreSQL 18 for confirmed fresh installations. Existing PostgreSQL 17 installations must retain their earlier source, storage mapping and verified backup until an installation-specific migration is reviewed. Do not start v2 against populated legacy storage or initialize a new volume as a substitute for migration. Follow the [setup and recovery guide](SETUP.md) before running any initialization command.

Verify the downloaded checksum before extraction. On Linux:

```sh
sha256sum -c basic_2.0.0_source.zip.sha256
unzip basic_2.0.0_source.zip
cd basic-2.0.0
```

On macOS, use `shasum -a 256 -c basic_2.0.0_source.zip.sha256` for checksum verification.

On PowerShell, compare `(Get-FileHash basic_2.0.0_source.zip -Algorithm SHA256).Hash` with the checksum file, then use `Expand-Archive basic_2.0.0_source.zip`.

Install Node.js 24.x or 26.13.1+ within 26.x, pnpm 11.19.0, Git and Docker Compose with Linux containers. Use a clean terminal without inherited database, Compose, Docker or dotenv selectors and inspect prior installations as required by [local setup](SETUP.md). Only after confirming that no existing Basic database contains data, run the guarded fresh initialization:

```sh
pnpm install --frozen-lockfile
node scripts/setup-env.mjs
node scripts/confirm-postgres18-fresh.mjs local
pnpm db:migrate
pnpm catalog:curate
pnpm build
pnpm start
```

Enter the helper's exact confirmation phrase only when its fresh-install conditions are true. It refuses existing project containers, populated legacy/target storage and inconsistent environment configuration. It is not a migration tool and cannot discover other projects, hosts, bind mounts or remote databases. Never fabricate an initialization marker or retry an interrupted fresh initialization by deleting storage.

The default app address is `http://localhost:3400`; `/ready` reports readiness and 30 profiles after curation. The guarded helper validates the default database origin/port. Custom ports, contexts or storage mappings need a separately reviewed procedure; do not bypass its checks to resolve a port conflict. Preserve existing databases and private environment files.

## Try the supported journey

1. Search for **I need a tool to search GitHub issues** and open the GitHub profile.
2. Inspect publisher sources, their dates, deployment requirements and verification history. Fresh curation starts with **Not tested** evidence; archived reports are not imported as new observations.
3. Try the documentation preset, open Microsoft Learn and expand a setup template. Configuration copying and JSON syntax do not prove installation in a third-party client.
4. Connect an SDK client to `http://localhost:3400/mcp`, or run `pnpm test:mcp` against your own running instance. The command lists and calls all three catalog tools and compares search results with the web API. It does not execute a publisher's tools.

Filters preserve explicit unknowns. A query such as **I need a tool for quantum gardening** returns no suitable matches. Missing profiles and malformed requests return bounded errors. Catalog evidence describes the recorded source or protocol observation; it does not certify third-party safety or guarantee task completion.

## Refresh and recover

Edit source-dated profiles and run `pnpm catalog:curate` for an offline catalog update. `catalog:sync` and `catalog:check` are explicit live operator actions with different scopes; read [OPERATIONS.md](../OPERATIONS.md) before running them. Adding a profile does not approve its endpoint for checking.

Run `pnpm backup:test` for a disposable local PostgreSQL dump/restore check. Set `BASIC_DB_CONTAINER` when using a named Compose project. The check compares table counts and verifies full-text search after restoration, then removes its temporary database. Preserve and test an independent backup before upgrading a database you need to retain.

The [Linux deployment guide](../DEPLOYMENT.md) covers containers, HTTPS, a scheduled worker and backups. Those instructions require validation on the chosen host. A source release does not establish public HTTPS, firewall rules, an off-host backup, production rollback or production capacity. The separate [hosted Sites edition](https://basic-agent-tools.alx21.chatgpt.site) uses its own reviewed snapshot and deployment process.

The helper's offline validation suite is POSIX-only and skips on Windows. A Windows application run against a separately reviewed disposable PostgreSQL fixture does not exercise the default fresh-install path. CI validates the Linux guard/helper and database recovery paths before publication; preserve that distinction when recording installation evidence.

## Historical v1.0.0 checkpoint

The October 6, 2026 local candidate check used Windows, Node 24.19.0, pnpm 11.19.0 and PostgreSQL 17.6 in a disposable Docker project. Frozen installation, dependency audit, 52 tests, typecheck and the production build passed. Eight desktop/mobile browser journeys passed, followed by real HTTP SDK calls to all three catalog tools, 35 search acceptance cases and all 30 profile routes. A fresh GitHub search/profile journey displayed the original September 9 source date and **Not tested** evidence. The local dump/restore preserved 30 profiles, 30 registry records and 122 claims and returned full-text search results.

Those dated observations cover the v1 source application. They do not verify v2's PostgreSQL 18 initialization, an installed Basic plugin connection in the current chat, or a production Linux deployment. The old archive and its recorded results remain unchanged.

## Current release automation

Pull requests and manual workflow runs validate without publishing. A main push can publish the stable package version, currently `v2.0.0`, after application validation (audit, tests, browser, SDK, acceptance, recovery and containers), PostgreSQL guard/helper checks and source packaging pass. CI checks both Node 24.19.0 and 26.13.1 and an independently extracted source consumer. The publisher uses only artifacts from that run, checks SHA256, rejects a tag or draft belonging to another commit, verifies uploaded assets, and leaves an existing published release unchanged. It also verifies that main still points to the validated commit before creating or updating a draft, creating a tag, and publishing.

After changing source for a future release, update the stable package version and changelog together. Commit a clean tree before running `pnpm package:release`; Git's archive includes committed files only. Private environment files, dependencies, build output and local backups are excluded from the source package.
