# PostgreSQL 18 migration rehearsal

This synthetic test does not upgrade an installation. Basic's local and production Compose files still use PostgreSQL 17. Do not switch the image tag on an existing volume: major PostgreSQL versions use incompatible on-disk formats, and the official 18 image uses a different default data-directory layout.

From a clean checkout without `.env` or `.env.local`, using Node 24, frozen dependencies and a local Docker engine, run `node scripts/rehearse-postgres-18.mjs`. The script creates random, isolated containers and volumes with loopback-only test ports and fictional catalog data. It creates synthetic admin, operator and reader roles using `deploy/db-init.sh`, applies the real migrations as the operator, then dumps a quiescent PostgreSQL 17 fixture. It verifies that PostgreSQL 18 refuses to open the old cluster and restores the dump into a separate PostgreSQL 18 cluster with newly created fixture roles. It checks data, migration state, table ownership, reader access, rate-bucket write permission and rejection of reader writes to catalog profiles. A synthetic post-cutover profile is absent when the old PostgreSQL 17 volume is restarted. The script stops its containers and retains its uniquely named test resources for inspection.

The first test uses a custom-format dump retaining ACLs and restores object ownership after recreating the same fictional roles. The production backup service in `deploy/backup.sh` uses `--no-owner --no-acl`: `--no-acl` omits grants, while PostgreSQL ignores `pg_dump --no-owner` for custom archives. The documented production restore separately passes `pg_restore --no-owner --no-acl`, so it does not reapply object ownership or grants. `pg_dump` does not recreate cluster-wide roles. In a second fixture restore using those flags as the admin, the reader cannot query restored profiles even though it exists. A third fixture assigns a fresh schema to the operator, restores as that role, explicitly reapplies the reader grants and confirms the synthetic role tests pass. These demonstrate two configurations; they do not prove all restoration roles, custom privileges or installations behave identically. Recreating or reapplying production roles, ownership, grants and default privileges requires an independently tested, installation-specific restore. Merely rerunning the checksum-tracked migration command will not rerun already recorded grant statements. The rehearsal does not establish that a production backup can be restored safely as-is. See the [PostgreSQL 17 pg_dump documentation](https://www.postgresql.org/docs/17/app-pgdump.html).

Before planning a real transition, an operator must:

1. Identify the actual host, Compose project, database container, image, `PGDATA`, mount source/destination, backup destination and all writers for each installation. Local and production Compose files are distinct. Custom project names, overrides, bind mounts, external volumes or remote databases require their actual mappings; never infer the active source from a default volume name or initialize a replacement by guessing.
2. Inventory roles and authentication, table/sequence ownership, grants and default privileges, extensions, collations, schema checksums, data and storage capacity. Quiesce the app, worker and every other writer. Record the recovery point and approved downtime.
3. Take protected, independently stored backups and verify a separate isolated restore of the exact data. Decide and rehearse how to recreate roles and restore ownership and grants, including reader access and rate-bucket writes, for the backup format actually used. Validate search, migrations, runtime role restrictions, worker behavior, readiness, the real SDK and backup operation before changing connections.
4. Rehearse the complete version-specific procedure against a separate PostgreSQL 18 target with the installation's actual mappings and compatible application. Do not mutate or restore over the sole existing copy.
5. Establish the rollback and reconciliation plan before allowing writes. The retained 17 volume contains only the pre-cutover state; restarting it after 18 has accepted writes discards later catalog, sync, verification and rate-limit changes. Stop writers and explicitly account for those changes and the accepted recovery point before switching back.

The backup and deployment guidance in [OPERATIONS.md](../OPERATIONS.md) and [DEPLOYMENT.md](../DEPLOYMENT.md) remains authoritative. This synthetic fixture does not test real credentials, live traffic, existing storage, hosted Sites, operational backups or a deployed application, and does not authorize or prove a production cutover.
